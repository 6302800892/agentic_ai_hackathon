# Compliance Mapping — EU AI Act · NIST AI RMF 1.0 · India DPDP Act 2023

**Scope and posture.** This is a hackathon system that runs on synthetic data only. The mapping shows how each
obligation *would* be met in production and points to the committed control that implements it today. It is
an engineering mapping, not legal advice.

**EU AI Act classification.** The copilot routes patient requests and escalates urgent ones. It doesn't diagnose,
so it is designed to stay outside medical-device scope. Because it prioritises healthcare access, it sits next
to Annex III §5 (access to essential services, and patient triage). We therefore apply the high-risk obligations
(Art. 9–15) voluntarily, plus the Art. 50 transparency duty.

## Digital Personal Data Protection Act, 2023 (India)

| Section / obligation | How it is addressed | Evidence artifact |
|---|---|---|
| s.4–6 Lawful purpose and consent | Processing is limited to care coordination. Production requires a consent capture step at intake, which isn't needed for synthetic data. | `docs/model-card.md` (intended use) |
| s.5 Notice | The AI disclosure is shown with every response. A production notice would add the purpose and rights. | `src/state.py` (`FinalResponse.disclosure`) |
| s.8(3) Accuracy and completeness | Coverage is decided from the record by deterministic rules; gaps come with rule ids | `mcp_server/store.py` |
| s.8(4)–(5) Security safeguards | PHI masked at ingress, logs, traces and output; HMAC pseudonyms; session-scoped tool access; secret hygiene | `src/guardrails/phi.py`, `mcp_server/store.py`, `.gitignore` |
| s.8(6) Breach intimation | Access-denied and guardrail-block events are audited, which is the detection signal for a breach runbook | `logs/agent_actions.jsonl` |
| s.8(7) Storage limitation and erasure | Long-term memory keeps only non-clinical, masked facts per patient. `python -m src.cli forget --patient <id>` erases them. Local state is git-ignored. | `src/memory/long_term.py`, `src/cli.py`, `.gitignore` |
| s.9 Children's data | Parents booking for a child are recorded only as a relationship fact, with no child identifiers. Production needs verifiable parental consent. | `src/memory/long_term.py` (`rule_based_facts`) |
| s.11–13 Data-principal rights (access, correction, erasure, grievance) | Erasure is implemented. Access and correction go through the front desk (CP-ADMIN-001), and the grievance officer is named in the production notice. | `data/policy_corpus/CP-ADMIN-001.md`, `src/cli.py` |
| Data minimisation | The MCP server returns only coverage-relevant fields; name, DOB, contact details and MRN never leave `mcp_server/store.py` | `mcp_server/schemas.py` (`PatientRecordOut`), `tests/test_tool_contracts.py` |

## Secrets management and rotation
- **Current state.**
  - Configuration comes from environment variables loaded with `python-dotenv` (`src/config.py`).
  - `.env` is git-ignored and `.env.example` documents every variable.
  - `scripts/verify_citations.py` scans the repository for Google API keys, private keys and hard-coded tokens
    on every regeneration.
- **Rotation plan (not in scope to build).**
  - Keep `GOOGLE_API_KEY` and `PHI_HMAC_SALT` in a managed secret store and inject them at start-up.
  - Rotate the API key every 90 days, and immediately on suspected exposure. Revoke the old key after the new one
    is verified.
  - Rotating `PHI_HMAC_SALT` changes every `patient_ref` pseudonym, so it needs a re-keying job for long-term
    memory (read under the old salt, write under the new one).
